# 00. メモリの配置 (フラッシュと SRAM)

ビルドしたプログラムが、ATtiny1604 のどこに、どう置かれるかをまとめます。例には `firmware/01-pwm-led-intr` を使います。

ATtiny1604 のメモリは、次の2つです。

| メモリ | 容量 | 内容 | 電源を切ると |
|---|---|---|---|
| フラッシュ | 16KB | プログラム (命令と定数) | 残る |
| SRAM | 1KB | 実行中の変数とスタック | 消える |

## 1. 3つのセクション

コンパイラとリンカは、プログラムを「セクション」に分けて配置します。主なものは次の3つです (定数の `.rodata` については 5 節)。

| セクション | 中身 | 例 (01-pwm-led-intr) | フラッシュ | SRAM |
|---|---|---|---|---|
| `.text` | 命令 (コード) | `main`、割り込み処理 | ここに置かれ、ここで実行される | ― |
| `.data` | 初期値のあるグローバル変数・static 変数 | `static int8_t dir = 1;` | 初期値を保存しておく | 起動時に、フラッシュからコピーされる |
| `.bss` | 初期値のない (0 の) グローバル変数・static 変数 | `static uint8_t level;`、`static volatile uint16_t cycles;` | 何も置かない (0 なので保存は不要) | 起動時に、0 で埋められる |

関数の中のふつうのローカル変数は、どのセクションにも入らず、実行中にスタック (SRAM の上の方) に置かれます。

**命令はフラッシュから直接実行されます。** PC では、SSD などに保存したプログラムを、いったん DRAM にロードしてから実行します。マイコンでは、フラッシュが CPU の命令用のバスに直接つながっていて、CPU はフラッシュから1命令ずつ読み出して実行します (XIP: eXecute In Place)。リセットすると、フラッシュの 0 番地から実行が始まり、ロードの手順はありません。AVR は、命令のバス (フラッシュ) とデータのバス (SRAM) が別々のハーバード・アーキテクチャで、命令の読み出しと変数の読み書きを同時に行えます。フラッシュは実行中には書き換えられないので、書き換える変数 (.data と .bss) だけを SRAM に置きます。

フラッシュから直接実行するのは、マイコンの基本的な方式です。RP2040 も同じ考え方ですが、チップの外の QSPI フラッシュから、キャッシュを通して実行します (速さが必要な処理は、SRAM にコピーして実行することもできます)。

## 2. フラッシュの配置

```
アドレス    中身                                       セクション       サイズ
0x0000   +- 割り込みベクタ (__vectors)                 .text
0x007C   |  起動処理 (スタックの設定、__do_copy_data、
         |           __do_clear_bss)
0x00BA   |  TCB0 の割り込み処理 (__vector_13)
0x0162   |  main と各関数
0x0980   +- 定数 (printf の文字列など)                 .rodata          115 バイト
0x09F3   +- .data の初期値 (SRAM へコピーする元)       .data の元        16 バイト
0x0A03   +- ここまで使用 (2563 バイト)
  ...       空き
0x3FFF      フラッシュの終わり (16KB)
```

- 割り込みベクタは、割り込みごとの飛び先の表です。`ISR(TCB0_INT_vect)` で書いた処理は `__vector_13` という名前になり、表から呼ばれます。
- 起動処理は、`main` より前に実行されます。`__do_copy_data` が `.data` の初期値を SRAM にコピーし、`__do_clear_bss` が `.bss` を 0 で埋めます。

## 3. SRAM の配置

```
アドレス    中身                                              サイズ
0x3C00   +- .data (dir、uart_stdout)                          16 バイト
0x3C10   +- .bss  (cycles、ms_count、level、__iob)            10 バイト
0x3C1A   +- ここから上は空き (malloc を使えばヒープになる)
  ...    |
         |  ^ スタック (関数の呼び出し、ローカル変数) は
0x3FFF   +-   上から下へ伸びる
```

- `uart_stdout` は `firmware/common/uart.c` の `FILE` 構造体 (printf の出力先) で、`__iob` は avr-libc の stdin/stdout/stderr のポインタです。
- スタックが下へ伸びて `.bss` にぶつかると、変数が壊れます (スタックオーバーフロー)。SRAM は 1KB しかないので、大きな配列をローカル変数にしないよう注意します。
- ツールの出力 (ELF ファイル) では、SRAM のアドレスに `0x800000` が足されて、`0x803C00` のように表示されます。フラッシュのアドレスと区別するための、AVR のツールの約束です。

## 4. アドレスが決まる仕組み

変数の SRAM の番地は、**実行するときではなく、ビルドする (リンクする) ときに決まり、命令の中に直接書き込まれます。** `01-pwm-led-intr` の変数 `level` を例に、順に追います。

### 4.1 ソース

```c
static uint8_t level;             /* 初期値なし -> .bss  */
static int8_t  dir = 1;           /* 初期値あり -> .data */
static uint8_t ms_count;          /* 初期値なし -> .bss  */
static volatile uint16_t cycles;  /* 初期値なし -> .bss  */
...
TCA0.SPLIT.HCMP0 = gamma_2(level);   /* level を読む */
```

### 4.2 コンパイル: 番地はまだ空欄

`main.c` をコンパイルした `main.o` (リンクする前のファイル) を見ると、`level` を読む命令は、番地が `0x0000` の空欄になっています。

```
80 91 00 00    lds  r24, 0x0000
               R_AVR_16  level      <- 「ここに level の番地を入れる」という印
```

この時点でわかっているのは、「`level` は main.o の .bss の、先頭から 3 バイト目」ということだけです。セクションの中の並び順は、ソースに書いた順とは限らず、コンパイラが決めます。

| 変数 | main.o の中のセクション | セクションの先頭からの位置 |
|---|---|---|
| `dir` | .data | 0 |
| `cycles` | .bss | 0 (2バイト) |
| `ms_count` | .bss | 2 |
| `level` | .bss | 3 |

### 4.3 リンク: 番地を決めて、空欄を埋める

リンカは、すべての .o と、ライブラリ (avr-libc など) の .data と .bss を集めて、SRAM の先頭 `0x3C00` から順に並べます。

```
番地     変数           出どころ
0x3C00   dir            main.o の .data
0x3C01   uart_stdout    uart.o の .data (14バイト)
0x3C10   __iob          avr-libc の .bss (6バイト)     <- ここから .bss
0x3C16   cycles         main.o の .bss (2バイト)
0x3C18   ms_count       main.o の .bss
0x3C19   level          main.o の .bss                 <- main.o の .bss の先頭 0x3C16 + 3
0x3C1A   (ここまで)
```

`level` の番地が `0x3C19` に決まったので、リンカは 4.2 の空欄を埋めます。

```
リンク前:  80 91 00 00    lds  r24, 0x0000
リンク後:  80 91 19 3c    lds  r24, 0x3C19
```

命令のバイト列を分解すると、次のとおりです (AVR は下位バイトが先に並びます)。

| バイト | 意味 |
|---|---|
| `80 91` | `0x9180`: 「SRAM から r24 に読む (lds)」という命令 |
| `19 3c` | `0x3C19`: 読む番地 (level) |

並べ方の指示を出しているのは、次の2つです。

- **リンカスクリプト** (binutils が用意する `/usr/lib/avr/lib/ldscripts/avrxmega3.xn`): 「.data は SRAM に置き、初期値はフラッシュに保存する」「.bss は .data のすぐ後ろ」といった並べ方
- **device-specs** (GCC が用意する、チップごとの設定ファイル): `-mmcu=attiny1604` を指定すると読まれ、「このチップの SRAM の先頭は 0x3C00」をリンカに伝える

### 4.4 起動: 決まった番地に、中身を用意する

番地はもう決まっているので、起動処理がするのは、その番地の中身を正しくすることだけです。

- `__do_copy_data`: フラッシュの `0x09F3` (.data の初期値) から、SRAM の `0x3C00` へコピーする。これで `dir` が 1 になる。コピー元とコピー先の番地も、リンカが計算して命令に書き込んだもの
- `__do_clear_bss`: `0x3C10` から `0x3C19` までを 0 で埋める。これで `level` などが 0 になる

PC では、実行するときに OS がメモリの場所を決めますが、マイコンでは、すべての番地がビルドした時点で決まっています。

### 4.5 自分で確かめる

```sh
cd firmware/01-pwm-led-intr
avr-gcc -mmcu=attiny1604 -DF_CPU=3333333UL -Os -I../common -c main.c -o main.o
avr-objdump -dr main.o         # リンク前: 番地が空欄 (R_AVR_16 の印)
make
avr-objdump -d pwm-led-intr.elf | grep 3C19   # リンク後: 番地が入っている
avr-nm -n pwm-led-intr.elf     # 変数の番地の一覧
```

## 5. 定数 (.rodata) はフラッシュのまま読める

`printf` に渡す文字列などの定数は `.rodata` セクションに入り、**フラッシュに置かれたまま**で、SRAM にはコピーされません。

- tinyAVR 1-series は、フラッシュを、SRAM や周辺機能のレジスタと同じアドレス空間の `0x8000` 以降にも見せています。ふつうの読み出し命令で、フラッシュの定数を直接読めます。
- そのため、`.rodata` のアドレスは、フラッシュの位置 (`0x0980`) に `0x8000` を足した `0x8980` になっています。
- 文字列をたくさん使っても、SRAM は減りません。
- 古い AVR (ATmega328 など) では、定数の文字列も SRAM にコピーされるため、`PROGMEM` という特別な書き方でフラッシュに残す必要がありました。tinyAVR 0/1/2-series では不要です。

## 6. 変数がないとき (00-blink)

`00-blink` には、グローバル変数も static 変数もありません。

| セクション | 00-blink | 01-pwm-led-intr |
|---|---|---|
| `.text` | 216 バイト | 2432 バイト |
| `.rodata` | なし | 115 バイト |
| `.data` | なし | 16 バイト |
| `.bss` | なし | 10 バイト |

`.data` と `.bss` がないので、起動処理の `__do_copy_data` と `__do_clear_bss` も、リンカが省いています。

## 7. 自分で調べる方法

コンテナの中で、ビルドしてから次のコマンドを実行します。

```sh
cd firmware/01-pwm-led-intr
make
avr-objdump -h pwm-led-intr.elf   # セクションの一覧 (サイズとアドレス)
avr-nm -n pwm-led-intr.elf        # 関数と変数のアドレス (アドレス順)
```

- `avr-objdump -h` の `VMA` は実行するときのアドレス、`LMA` はフラッシュに書き込まれるアドレスです。`.data` は、LMA (フラッシュの初期値) と VMA (SRAM) が違います。
- `avr-nm` の記号の意味は、`T`/`t` がコード、`D`/`d` が .data、`B`/`b` が .bss です (大文字は外から見える名前、小文字は static)。

## 8. avr-size の表示の注意

ビルドのときに表示される `avr-size` の `Program` は、`.text` と `.data` の合計で、**`.rodata` が含まれていません** (01-pwm-led-intr では 2448 バイト)。実際のフラッシュの使用量は、`.rodata` を足した 2563 バイトで、書き込みのときに avrdude が表示するバイト数と一致します。フラッシュの残りを気にするときは、avrdude の数字を見るのが確実です。

`Data` (SRAM の使用量、.data と .bss の合計) は正しく表示されます (01-pwm-led-intr では 26 バイト)。
